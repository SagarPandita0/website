cuda.fast on DGX Spark: real speedup, narrow claim

The cuda.fast leaderboard says Qwen3.8-Flash-Next now runs 108.5% faster on one DGX Spark. I built the exact promoted engine, verified the pinned 109 GB GGUF snapshot, ran its public harness three times, and recorded the entire box every five seconds.

The result is interesting for a reason bigger than one score: this is a purpose-built inference engine that keeps the useful weights resident, reads a giant lookup table from NVMe, and uses Qwen's own MTP head to finish more than one token per expensive model step.

the verdict

The number is real inside the benchmark, but the sentence is easy to overread. The official result is paired against a serial control on the same Spark, in the same job, with two control/candidate pairs and a calibrated health band. That is stronger than comparing against an old number from another machine.

What it does not mean is twice the speed for every prompt, context length, concurrency level, or serving stack. It is a decode-heavy composite for one single-stream benchmark shape.

credible, narrowly scopedNot inflated; insufficiently qualified if the score formula is omitted.

what is actually different

This is not vLLM with another launch flag, and it is not a general OpenAI-compatible server. The measured path is a compact engine and benchmark adapter built around this model and this GB10.

1 · GGUF shardsUnsloth UD-Q4_K_XL, checked byte-for-byte before launch.
2 · split residency76.87 GiB stays resident; the 26.82 GiB PLE table is read directly from NVMe.
3 · ds4 on GB10Custom CUDA kernels for Qwen's GDN, sparse attention, routing and quantized experts.
4 · native MTP headA 2.60 GiB Q8 head proposes the next token while the target model verifies it.
5 · resident protocolOne model load serves every harness phase through a local socket.

The promoted commit adds a GDN kernel that reuses one query/key vector and gate pair across four value rows. That saves repeated memory work without changing the ordered arithmetic for each row. The larger win is cumulative: model-specific kernels, SSD-aware layout, one-load residency, and speculative decode all compound.

my three runs

The public harness uses a 1,024-token long-copy prompt, greedy single-stream generation, MTP depth 1, a five-second timed window, and a cool gate before each timing phase. The official private prompt and serial control were not available locally, so these runs correctly sealed score: null.

the 108.5% claim

composite = prefill gain0.25 × decode gain0.75

The leaderboard reports (composite − 1) × 100%. “108.5% faster” therefore means a 2.085× weighted composite—not that both raw throughput numbers individually doubled.

memory trick

The model body is 103.69 GiB before the draft head and working memory. The engine avoids an impossible all-resident allocation by treating the huge per-layer n-gram embedding table as a sparse lookup file.

what I would—and would not—repeat

  • The engineering is substantive. The SSD split is model-aware, the resident process removes repeated 100 GB loads, and MTP converts a 90.9% accepted draft stream into fewer expensive target-model rounds.
  • The official comparison is well controlled. The serial denominator is measured beside the candidate, not copied from an old blog post. Calibration is a health check, not the denominator.
  • The headline needs its noun. “108.5% faster single-stream composite” is precise. “The model is 108.5% faster” invites a broader interpretation than the benchmark supports.
  • My run validates the engine, not the leaderboard score. The local harness intentionally cannot seal an official score without the organizer's reference tree, calibration and private golden.
  • It is not yet a drop-in server benchmark. There is no concurrency sweep, 256K context test, HTTP scheduling measurement or long-running production soak in this result.

method & sources

Machine: one NVIDIA DGX Spark, GB10, 128 GB unified memory, CUDA 13.0, driver 580.173.02. Candidate repository fb49cb2; pinned ds4 engine 5f36517; benchd source 206b71b. The model and harness hashes matched across all three runs. Seventy-nine adapter tests also passed.
